# Time Series Forecast Benchmark

A self-contained benchmark comparing six forecasting approaches — from a
trivial seasonal-naive baseline up through classical statistical models,
decomposition-based models, and gradient-boosted trees — on the same daily
sales series, evaluated on the same held-out test window.

Comes with a synthetic data generator, so it runs end-to-end with zero
external data dependencies — swap in your own CSV whenever you're ready.

## Models compared

| Model | Family | Notes |
|---|---|---|
| Seasonal Naive | Baseline | "Sales today = sales same weekday last week." Every other model should beat this. |
| ETS (Holt-Winters) | Classical statistical | Additive trend + weekly seasonality (`statsmodels`) |
| ARIMA | Classical statistical | `pmdarima.auto_arima` search over (p,d,q)(P,D,Q,m) |
| Prophet | Decomposition | Trend + yearly + weekly seasonality (Meta's Prophet) |
| NeuralProphet | Decomposition + AR-Net | Prophet-style decomposition plus a small autoregressive neural component |
| LightGBM | Gradient-boosted trees | Lag features (1/2/3/7/14 days) + rolling stats + calendar features, recursive multi-step forecasting |

## Results (synthetic demo data, 30-day holdout)

| Model | MAE | RMSE | MAPE (%) |
|---|---|---|---|
| Prophet | 6.80 | 8.09 | 1.83 |
| ETS | 7.67 | 9.82 | 2.06 |
| NeuralProphet | 12.79 | 15.81 | 3.46 |
| ARIMA | 14.74 | 16.74 | 3.96 |
| LightGBM | 17.66 | 19.77 | 4.74 |
| Seasonal Naive | 21.15 | 24.20 | 5.67 |

*(Numbers will vary slightly on your machine due to solver/training
randomness. All six models beat the seasonal-naive baseline on this
synthetic set, which has clean, strong weekly + yearly seasonality —
Prophet and ETS's built-in seasonal decomposition suits that structure well.
LightGBM's recursive multi-step forecasting accumulates error faster than
the decomposition models on a 30-day horizon; that's a real, expected
tradeoff of recursive tree-based forecasting, not a bug.)*

## Setup (VS Code)

1. Clone the repo and open the folder in VS Code.
2. Create a virtual environment:
   ```bash
   python -m venv .venv
   source .venv/bin/activate   # Windows: .venv\Scripts\activate
   ```
3. In VS Code, select the interpreter: `Cmd/Ctrl+Shift+P` → `Python: Select Interpreter` → choose `.venv`.
4. Install dependencies:
   ```bash
   pip install -r requirements.txt
   ```
   Prophet and NeuralProphet install `cmdstanpy`/`torch` respectively and
   compile/initialize on first use — the first run may take noticeably
   longer than subsequent ones.

## Usage

Generate the synthetic dataset:
```bash
python src/generate_data.py
```

Run the full benchmark (trains all six models, evaluates, saves plot + metrics):
```bash
python src/compare_models.py
```

Or use the pre-configured Run and Debug panel in VS Code — launch configs
for `Generate Data` and `Run Full Benchmark` are included.

Run tests:
```bash
pytest tests/ -v
```

## Using your own data

Replace `data/sales_data.csv` with your own file, keeping two columns:

| date | sales |
|---|---|
| 2024-01-01 | 245.10 |
| 2024-01-02 | 251.30 |

Then adjust in `src/compare_models.py`:
- `TEST_DAYS` — size of the holdout evaluation window
- `seasonal_period` in `ArimaForecaster` / `seasonal_periods` in `ETSForecaster` — `7` for daily data with weekly patterns, `12` for monthly data with yearly patterns
- `n_forecasts` in `NeuralProphetForecaster` — should match `TEST_DAYS` for a clean single multi-step forecast (see note below)

## Known limitations

- **NeuralProphet's multi-step forecast extraction is non-obvious.** NeuralProphet
  stores its `yhat1...yhatN` multi-step predictions on a diagonal across
  rows, not in a single row — `neuralprophet_model.py` handles this, but if
  you change `n_forecasts` independently of the prediction horizon, the
  extraction logic pads/truncates rather than raising, which can silently
  mask a mismatch. Keep `n_forecasts == periods` when calling `.predict()`.
- **LightGBM's recursive forecasting compounds error with horizon length.**
  Each predicted day feeds back in as a lag for the next, so accuracy
  degrades faster than the decomposition models over long horizons — expected
  behavior for tree-based recursive forecasting, not unique to this implementation.
- **NeuralProphet requires PyTorch 2.6+ compatibility shim.** PyTorch 2.6
  changed `torch.load`'s default `weights_only` behavior, which breaks
  NeuralProphet's internal checkpoint loading. `neuralprophet_model.py`
  patches this locally — safe here since checkpoints are created and
  consumed by the same trusted local process, but worth knowing if you
  reuse the module elsewhere.
- **No hyperparameter tuning.** `auto_arima`'s stepwise search and
  NeuralProphet/LightGBM's default hyperparameters are used as-is; a
  production system would tune these per-series.
- **Single train/test split, not rolling-origin cross-validation.** Metrics
  reflect performance on one 30-day window, not an average over multiple
  forecast origins.
